## Modos de Execução

**1. Sobre o modo standalone.**

R: O modo standalone utiliza apenas um único executor por nó worker por aplicação. Além disso, é correto dizer que o modo standalone possui um *cluster manager* gerenciando os recursos. A grande diferença do modo standalone para os demais é que, nele, nenhum outro *framework* além do Apache Spark deve existir. Isto é, caso o usuário precise utilizar o Apache Spark e o Apache Flink, por exemplo, o modo standalone não poderá ser utilizado.

## Ações e Transformações

**1. Ações, driver e *stage boundaries***.

R: Na dinâmica de uso do Spark, é correto dizer que as ações funcionam como gatilho para a execução de tarefas nos processos executores. Dessa forma, a completude ou a falha das tarefas exige que tais processos enviem dados ao *driver* para controle e gerenciamento. Ações não determinam diretamente os limites de um *stage*, isto é, não há uma relação direta de um *stage* para cada ação em uma aplicação Spark submetida. Normalmente, os *stages* são definidos por procesoss de *shuffle* causados por uma *wide transformation* no código.

## Reparticionamento

**1. Diminuir o número de partições normalmente reduz o tempo de execução de narrow transformations caso haja um número maior de processos executores do que partições.**

R: Não. Para *narrow transformations*, um número baixo de partições normalmente resulta em um maior tempo de execução caso haja mais executores do que partições. Uma *narrow transformation* não inclui *shuffle*, ou seja, dados não são trafegados entre executores. *Shuffles* são operações custosas e quase sempre podem ser consideradas como "gargalos" de fluxos de trabalho em Spark.

Diferente de processos de *shuffle* existentes em *wide transformations*, as *narrow transformations* são executadas por partição, existindo assim um processo executor para cada partição. Dessa forma, o número de executores disponíveis possui um grande efeito no processamneto da aplicação. Se o número de executores for maior do que o número de partições, por consequência, existirão executores no processo que não estarão desempenhando papel algum (*idle*).  Por outro lado, se o número de *executores* for **menor** do que o número de partições, a operação poderá ser finalizada apenas quando todos os executores finalizarem suas tarefas das partições designadas para que as partições restantes também possam ser processadas.

Para otimizar o tempo de processamento de uma aplicação contendo apenas *narrow transformations*, o ideal é configurar o número de partições do processo **igual** ao número de executores.

___

**2. Sobre as configurações de particionamento e o método `coalesce()`**

R: Uma operação de *shuffle* (*wide transformation* que exige tráfego de dados entre executores) retorna 200 partições se as configurações padrão forem mantidas (configuração `"spark.sql.shuffle.partitions"`). 

O método `coalesce()`, por sua vez, pode ser utilizado apenas para **diminuir** o número de partições, mas não para aumentá-las. Em linhas gerais, o método `coalesce()` evita um *full shuffle*, porém não está totalmente isento de uma operação *shuffle*, resultando também em trocas de dados entre executores.

## Processos de uma aplicação

**1. Sobre executores.**

R: Um executor persite apenas durante o ciclo de vida de uma aplicação e são específicos às mesmas. Em outras palavras, não há executores servindo múltiplas aplicações. Quando uma aplicação é finalizada, os executores também são finalizados.

Existe uma única exceção à essa regra relacionada à uma configuração de alocação dinâmica de recursos (*Dynamic Resource Allocation*) que, quando habilitada, permite que os executores permaneçam ativos mesmo ao final da aplicação. Tais executores são finalizados quando se tornam ociosos.

**2. Slots, tasks, cores e executores.**

R: Uma *Java Virtual Machine* (JVM) trabalhando como um processo executor pode ser considerada como um *pool* de *slots* para a execução de tarefas. Na prática, o Spark **não** cria e destrói *slots* de acordo com as cargas de trabalha. Para cada executor, os *slots* estão disponíveis de acordo com a quantidade de *cores* configuradas para cada processo executor (propriedade `spark.executor.cores`) e também quantas CPUs foram configuradas para cada tarefa (propriedade `spark.task.cpus`). Um *slot* pode expandir múltiplos *cores*. Se uma *task* requer múltiplos *cores*, então ela precisa ser executada através de um *slot* que expande múltiplos *cores*. Em um complemento, é possível dizer que as propriededes `spark.executor.cores` e`spark.task.cpus` paramatrizam o número máximo de tarefas que um executor pode processar simultaneamente. O número diponível de *slots* é calculado pela divisão entre o número de cores por executor e o número de cores por tarefa.

## Accumulators e broadcast variables

**1. Sobre os accumulators e o consumo de dados.**

R: Os valores de um *accumulator* podem apenas serem lidos pelo processo *driver*, mas não pelos executores. Na prática, não é possível utilizar uma variável *accumulator* para coordenar fluxos de trabalho entre executores. O uso canônico de uma variável deste tipo envolve processos de *debug* para o *driver*. Por exemplo, se for necessário contar valores que serão validados sob uma condição específica em uma UDF para propósitos de *debug*, então um *accumulator* pode ser um bom caso de uso.

___

**2. Breve definição sobre broadcasting**

R: Em cenários práticos, é comum encontrar a aplicação do processo de *broadcasting* em operações de *joins* que envolvem, ao menos, uma tabela pouco volumosa. Aplicar o *broadcasting* (com o auxílio da tradução da palavra para um melhor entendimento) significa "comunicar" ou "compartilhar" os dados desta tabela pequena (pense em uma tabela auxiliar) com todos os executores da aplicação, permitindo assim um rápido acesso aos dados desta tabela para cruzamentos otimizados.  A sintaxe segue algo como (considerando `df2` como uma tabela auxiliar): 

```python
df1.join(other=broadcast(df2), on=, how=)
```

___

**3. Breve definição sobre accumulators**

R: Uma aplicação Spark submetida é executada nos processos executores. Tais processos não possuem informações sobre variáveis fora de seu escopo (ex: uma UDF com contador `counter=0` que é incrementado dentro da função). Portanto, para funcionalidades deste tipo, é preciso informar explicitamente aos executores que um contador (como no exemplo) é uma variável compartilhada. Dessa forma um `Accumulator` que, por sua vez, é gerenciado pelo *driver* e acessível por todos os executores, pode se fazer presente. Um fator importante é que, se uma ação envolvendo um *accumulator* falha durante a execução e o Spark reinicia a ação para uma nova execução com sucesso, apenas a execução bem sucedida irá contar no *accumulator*.

## Out of memory

**1. Formas de evitar erros *out of memory.***

R1: Reduzir o tamanho da partição é uma forma viável de eliminar erros de sobrecarga de memória pois, visto que os executores carregam as partições para a memória antes de processá-las, partições volumosas podem sobrecarregas os executores. 

R2: Diminuir o número de *cores* disponíveis para cada executor pode auxiliar na diminuição de erros de sobrecarga de memória. Em linha com o cenário de carregamento das partições para a memória nos executores, é possível imaginar que a máquina de um nó do *cluster* estará servindo múltiplos executores com múltiplas tarefas simultâneas em múltiplos *cores* e com múltiplas partições sendo carregadas para a memória. Tudo em paralelo. Diminuir os *cores* disponíveis para cada executor pode aliviar o uso da memória em tais processos.

R3: Limitar o volume de dados serializados enviados ao *driver* também pode ser uma boa estratégia para evitar erros de sobrecarga de memória. Ao utilizar a ação `collect()` em um grande volume de dados, por exemplo, a quantidade de dados transmitidos ao *driver* pode ser gigantesca, causando sobrecarga de memória. Evitar comandos deste tipo é fundamental para aliviar esta sobrecarga. Além disso, configurações como as proporcionadas pelo parâmetro `"spark.driver.maxResultSize"` permite definir limites de transmissão de dados ao *driver*, fazendo com que os *jobs* sejam interrompidos se o limiar configurado for excedido.

R4: Limitar a quantidade de dados automaticamente considerados como parte do processo de *broadcasting* pode evitar erros de sobrecarga de memória. Como parte automática do processo de otimização interna, o Spark pode escolher aumentar a performance de operações através do processo de *broadcasting* em dados (principalmente tabelas pequenas) para os executores. Na teoria, isso auxilia na velocidade das operações. Entretanto, o processo de *broadcasting* indica o carregamento de tais tabelas no *driver*, em um primeiro momento. Se essas tabelas forem relativamente volumosas e em grandes quantidades, um erro de sobrecarga pode ser obtido no *driver*. Para evitar este comportamento, é possível utilizar o parâmetro `spark.sql.autoBroadcastJoinThreshold` para definir o tamanho máximo de tabela para que o Spark considere um *broadcasting* automático.

## Cache, persist, storage level e garbage collector

**1. A operação de ache é avaliada como uma transformação?**

R: Sim. `DataFrame.cache()` é avaliada como uma transformação de forma *lazily*, assim como as demais transformações. Isto significa que chamar `DataFrame.cache()` não possui efeito imediato até que uma ação seja codificada, como por exemplo, `DataFrame.cache().count()`.

___ 

**2. O básico sobre caching.**

R: Na prática, *caching* significa armazenar uma cópia de uma partição no processo executor para ser acessada de forma mais rápida em operações subsequentes ao invés de recalcular tudo novamnete. Por padrão, o método `DataFrame.cache()` considera o *storage level* MEMORY_AND_DISK. Para modificar o *storage level*, o método `DataFrame.persist()` pode ser utilizado.

## Adaptive Query Execution e Dynamic Partition Pruning

**1. O básico sobre *dynamic partition pruning***

R: *Dynamic partition pruning* atua como uma forma eficiente de aplicar uma consulta seletiva em processos de leitura de dados ignorando dados que não são relevantes para a *query*.  Em essência, é comum ver essa aplicação atrelada a processos de *joins* com variáveis *broadcast*

**2. O básico sobre Adaptive Query Exectuion**

R: *Adaptive query execution* otimiza planos de *queries* com base em estatísticas de execução coletadas durante a execução da consulta. Entre as funções do Adaptive Query Execution, é possível citar:

- Otimização de *skew joins* (joins com dados desbalanceados, nulos ou que formam partições de tamanhos totalmente diferentes).


Avaliar:

Spark does not automatically optimize skew joins by default.

This statement is correct. Automatic skew join optimization is a feature of Adaptive Query Execution (AQE). By default, AQE is disabled in Spark. To enable it, Spark's spark.sql.adaptive.enabled configuration option needs to be set to true instead of leaving it at the default false.

To automatically optimize skew joins, Spark's spark.sql.adaptive.skewJoin.enabled options also needs to be set to true, which it is by default.

When skew join optimization is enabled, Spark recognizes skew joins and optimizes them by splitting the bigger partitions into smaller partitions which leads to performance increases.

Broadcast joins are a viable way to increase join performance for skewed data over sort-merge joins.

This statement is correct. Broadcast joins can indeed help increase join performance for skewed data, under some conditions. One of the DataFrames to be joined needs to be small enough to fit into each executor's memory, along a partition from the other DataFrame. If this is the case, a broadcast join increases join performance over a sort-merge join.

The reason is that a sort-merge join with skewed data involves excessive shuffling. During shuffling, data is sent around the cluster, ultimately slowing down the Spark application. For skewed data, the amount of data, and thus the slowdown, is particularly big.

Broadcast joins, however, help reduce shuffling data. The smaller table is directly stored on all executors, eliminating a great amount of network traffic, ultimately increasing join performance relative to the sort-merge join.

It is worth noting that for optimizing skew join behavior it may make sense to manually adjust Spark's spark.sql.autoBroadcastJoinThreshold configuration property if the smaller DataFrame is bigger than the 10 MB set by default.
